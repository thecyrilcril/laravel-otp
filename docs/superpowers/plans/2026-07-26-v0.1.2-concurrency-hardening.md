# v0.1.2 Concurrency & Serialization Hardening — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the six findings from the 2026-07-26 security audit that survive scrutiny, restoring the brute-force, availability, timing, and single-use guarantees the package documents.

**Architecture:** No public API signature changes — `issueOtp`/`verifyOtp`/`consumeOtp` keep their shapes. Internals change substantially: the verify path stops holding a row lock across bcrypt (compare-and-delete instead), failure bookkeeping moves outside any transaction, limiter gates become atomic, and `IssuedOtp` refuses serialization.

**Tech Stack:** unchanged (PHP ^8.4, illuminate ^12|^13, Pest/testbench, MySQL 8 + sqlite in CI).

## Global Constraints

- **No public API signature changes.** This is a patch release; consumers must not have to edit call sites.
- `composer ci` green on sqlite AND the full suite green on MySQL (`DB_CONNECTION=mysql vendor/bin/pest`, local db `otp_test`) after **every** task. The MySQL leg is not optional here — three of these fixes are concurrency fixes that sqlite cannot meaningfully exercise.
- Existing behavioral guarantees that must not regress (all currently pinned by tests):
  - bare `false` on every failure; reasons only in `OtpVerificationFailed`
  - failed checks charge BOTH the limiter and the per-row `attempts` budget
  - `verifyOtp` non-destructive on success; `consumeOtp` single-use
  - success clears the verify limiter
  - throttled issue AND throttled verify/consume throw `OtpThrottledException`; throttled verify also fires the failed event with reason `Throttled`
  - purpose scoping; context binding semantics (null context ignores presented context)
- Plaintext codes must never appear in: DB rows, event payloads, exception messages, `var_dump`, `print_r`, `json_encode`, **and now `serialize`**.
- Every fix lands with a test that FAILS before it and passes after — these are security regressions, not features; an unproven fix is not a fix.
- Working directory: `/Users/user/Code/laravel-otp`, branch `feat/v0.1.2-hardening` off `main`.

## Audit findings this plan addresses

Verified by the controller before planning (not taken on the auditor's word):
- **F1** attempts increment rolls back with a consumer transaction — reproduced in kitwire: `attempts_after_one_wrong_guess => 0`.
- **F2** limiter check-then-hit TOCTOU — `RateLimiter::increment()` confirmed to return post-increment hits, so an atomic gate is available.
- **F3** bcrypt inside the transaction holding the row lock.
- **F4** `Expired` branch returns before any hash (un-equalized timing).
- **F5** `serialize()` leaks plaintext — reproduced: `serialize leaks plaintext: YES` while json/print_r are clean.
- **F6** concurrent issue can leave two live rows; unordered `first()` + single-row delete can leave a valid code alive after consume.

Deliberately NOT in scope (documentation-only or lower value, deferred to a follow-up): F7 bigint index binding, F8 purpose length validation, F9 README leaked-DB scoping + `length: 8` guidance, F10 context sensitivity note, F11 config `env()` caution.

### Task 1: Restructure the verify path — no bcrypt under lock, durable bookkeeping

**Files:**
- Modify: `src/Concerns/HasOtps.php`
- Test: `tests/VerifyOtpTest.php`, `tests/ConsumeOtpTest.php` (both must stay green unmodified — they are the regression net)
- Test: `tests/ConcurrencyTest.php` (new)

**Interfaces:**
- Consumes: `Otp` model, `OtpLimiter` (Task 2 changes it — this task must not depend on the new signatures), `FailureReason`, events.
- Produces: a `checkOtp` whose transaction (if any) contains only the final compare-and-delete; `verifyOtp`/`consumeOtp` signatures unchanged.

**Approach (addresses F1, F3, F6):**

Current shape: `DB::transaction { lockForUpdate → first → failureReasonFor (bcrypt!) → increment attempts / delete → return reason }` then events outside.

New shape, no transaction and no row lock at all:

1. `guardVerify` (unchanged position — before everything).
2. **Read** the candidate row without locking, deterministically ordered:
   `$otp = $this->otps()->where('purpose', …)->latest('id')->first();`
   (`latest('id')` fixes F6's non-determinism — always the newest code, matching the one the user was last mailed.)
3. Compute `failureReasonFor(...)` **outside any transaction** — the bcrypt happens here, holding nothing (F3).
4. On failure: bookkeeping runs **outside any transaction** (F1) — `recordAttemptOnFailure` then limiter then event. The increment must be a direct atomic UPDATE, not read-modify-write:
   `$affected = Otp::whereKey($otp->getKey())->increment('attempts');` and re-read `attempts` (or compute) to decide deletion; delete when `>= max_attempts`.
   **Durability note:** a consumer transaction wrapping the call can still roll this back — PHP cannot escape an outer transaction on the same connection. Task 5 documents this explicitly and Task 1 must NOT silently pretend otherwise. What this task removes is the *package's own* transaction as a cause.
5. On success:
   - `verifyOtp`: no write at all. Clear limiter, fire `OtpVerified`, return true.
   - `consumeOtp`: **compare-and-delete** — `$deleted = Otp::whereKey($otp->getKey())->where('attempts', $otp->attempts)->delete();` If `$deleted !== 1`, another request consumed it first: return false with `FailureReason::NotFound` (do NOT fire `OtpVerified`). Only on `$deleted === 1` clear the limiter, fire `OtpVerified`, return true. This preserves single-use atomically with zero lock hold.
   - Additionally (F6): after a winning consume, delete any *other* rows for the same model+purpose so a concurrently-issued second code cannot survive a successful consume:
     `$this->otps()->where('purpose', …)->delete();`

Remove the `DB` import if nothing else in the trait uses it (`issueOtp` still does — keep it).

**Patterns to follow:** the existing `failureReasonFor` purity (no side effects) is preserved and becomes load-bearing now that it runs unlocked.

**Test scenarios (new `tests/ConcurrencyTest.php`):**
- Compare-and-delete: consume a code, then attempt to consume the *same* code object again (simulating the loser of a race by consuming twice from two model instances of the same user) → exactly one `true`, one `false`, one `OtpVerified` event total.
- After a successful consume, no rows remain for that model+purpose even when two rows existed beforehand (insert a second row manually to simulate the F6 race).
- `latest('id')` determinism: with two rows present, the newest code verifies and the older one does not.
- Attempts bookkeeping without any package transaction: 5 wrong guesses (clearing the limiter between) still deletes the row — the existing `VerifyOtpTest` case must remain green, proving no regression.
- A wrong guess increments `attempts` by exactly 1 (guards against double-increment in the restructure).

**Verification:** `vendor/bin/pest` green on sqlite; `DB_CONNECTION=mysql vendor/bin/pest` green. No `lockForUpdate` remains in `src/`.

### Task 2: Atomic limiter gates

**Files:**
- Modify: `src/Support/OtpLimiter.php`
- Modify: `src/Concerns/HasOtps.php` (call-site adjustment only)
- Test: `tests/OtpLimiterTest.php` (update — semantics change deliberately)

**Interfaces:**
- Consumes: Illuminate `RateLimiter` (`increment($key, $decay)` returns post-increment hit count — verified).
- Produces:
  - `guardIssue(Model, OtpPurpose): void` — atomically increments then throws if over. (Signature unchanged.)
  - `guardVerify(Model, OtpPurpose): void` — **now atomically increments then throws if over.** Behavioral change.
  - `clear(Model, OtpPurpose): void` — unchanged; refunds the budget on success.
  - `recordFailure()` — **removed**; the increment is now part of `guardVerify`. Remove its call site in `HasOtps` and its test.

**Approach (addresses F2):** replace check-then-hit with increment-then-compare in both guards:

```php
if ($this->limiter->increment($key, $decay) > $max) {
    throw OtpThrottledException::retryIn($this->limiter->availableIn($key));
}
```

Semantic consequences to accept and document:
- A *successful* verify now consumes one unit of budget before `clear()` refunds it — net zero for legitimate users.
- The verify limiter now counts attempts, not just failures. With `attempts: 5` the 6th attempt in a window throws, same observable ceiling as before.
- The existing test `guardVerify alone never records attempts` becomes false by design — **replace** it with `guardVerify is itself the gate: N calls past the limit throw`, and note in the commit why the old assertion was inverted (it pinned the TOCTOU).

**Test scenarios:**
- N concurrent-shaped calls: 5 `guardVerify` calls pass, the 6th throws (no `recordFailure` needed).
- `guardIssue` unchanged externally: 3 pass, 4th throws with positive retry-after.
- `clear()` after success restores budget (verify succeeds repeatedly without exhausting the limiter — pin with a loop of ≥6 successful verifies).
- Per-user and per-purpose scoping still isolated.
- Existing `VerifyOtpTest`/`ConsumeOtpTest` throttle cases stay green.

**Verification:** both drivers green.

### Task 4: Seal `IssuedOtp` against serialization

**Files:**
- Modify: `src/IssuedOtp.php`
- Test: `tests/IssuedOtpTest.php` (extend)

**Approach (addresses F5):** implement `__serialize(): array` to throw `LogicException` with a message naming the correct usage:

```
IssuedOtp must not be serialized — read ->code immediately and discard the object.
Serializing it would write the plaintext OTP into queue payloads, sessions, or cache.
```

Rationale for throwing rather than masking: the object's contract is a one-time, in-request exposure. A masked serialization would silently produce an `IssuedOtp` whose `->code` is `******` on the far side — a confusing bug. Throwing surfaces the misuse at the moment it happens. `__serialize` (not `__sleep`) is used so it also covers `var_export`-adjacent paths and modern serialization.

**Test scenarios:**
- `serialize($issued)` throws `LogicException` (test asserts the exception, and that no plaintext escapes).
- `json_encode` still masks (regression).
- `__debugInfo`/`print_r` still masks (regression).
- Direct property access `->code` still returns plaintext (the object must remain usable for its one job).

**Verification:** both drivers green.
